# Desk core

Plain TypeScript and Bun's built-in SQLite. No AI, network calls, third-party dependencies, or credentials. All test identities and content are fictional SAMPLE data.

Run from this directory with Bun (implemented and tested on 1.3.14):

```sh
bun test
```

Import the public API from `src/index.ts`. Create a `Store(path)`, register project identities and unique studio/client room IDs, then construct `Desk(store, transport, deployer)` and `StageMachine(store)`. Configuration is immutable for a given database. Close the store on orderly shutdown. Use one active runtime/Store per database; opening a store is startup recovery and marks outstanding intents uncertain.

- `createDraft({project, destinationRoomId, text, attachments, threadId?})` snapshots and deeply freezes its content, binds the project's client destination, and returns an immutable draft with a 10-character hash-derived code (extended on collision). `threadId` defaults to `default`; revisions supersede active drafts in the same project/thread. Attachment names must be unique; hashes are lowercase SHA-256 of actual file bytes. Canonical JSON has a fixed field order and preserves attachment order.
- `handleMessage({senderId, senderKind, roomId, body, eventId})` accepts only the exact commands `@desk send <code>` and `@desk deploy <full-lowercase-40-character-sha>` from the configured human owner in that project's studio. Rejections are recorded with fixed reasons, without message bodies or exception details. No network identity is inferred from body text.
- `recordReview(commitSha, verdict, reviewId, projectId?)` is a trusted review-stage input, not a chat command. Three arguments work for a single-project store; a multi-project store requires the fourth project ID to prevent cross-project review reuse. Verdicts are `pass` or `fail`; the latest review for an exact SHA controls deployment. Reused review IDs must describe the same review.
- `postFixedLine(project, "ticketAssigned", {n}, eventId)` is a trusted internal event path. Only a positive safe integer can enter `Ticket #{n}: assigned to Varun`. Arbitrary template names, strings, or extra keys are rejected. No client/agent text should dispatch this API.
- Stage methods are `get(project)`, `question(project)`, `suggest(project, stage, artifact, options?)`, and `approve(project, stage, version, artifact, actor)`. Actors carry verified sender ID/kind and room ID. Suggestions increment a version and clear its approvals; a scope change clears and increments all later stages by default, or only `affectedStages` when explicitly supplied by the trusted workflow adapter. Unaffected approvals remain effective. Questions preserve state. Only the current stage/version/exact artifact can be approved. Brief and video require owner then client; architecture, build, and learn require owner; client review requires a registered client. Commit artifacts for build/client review require a confirmed deployment for the same project and SHA; video artifacts require a SHA-256 file hash. Initial empty stage records are version 1; first publication through `suggest` creates version 2.

`Transport.prepare` resolves the actual outgoing text and file bytes. The core snapshots the bytes, hashes them, compares the complete content to the frozen draft, then calls `Transport.send` with that verified snapshot and the bound destination. Adapters must send exactly those bytes and text, without fetching or substituting files again. Every transport/deployer call follows a durable intent. Providers must not silently retry unless they honor `deliveryId`/`intentId` as an idempotency key.

Confirmed sends never repeat, even with a new approval event after restart. Duplicate event IDs are ignored across all entry paths. A crash or ambiguous provider error leaves an uncertain intent; startup never resends it. The owner can explicitly approve the same active code using a new event ID. That is a new authorized attempt: if the original request reached the provider before acknowledgement was lost, it can produce a duplicate externally. This is a recorded uncertainty, not a claim of atomic exactly-once delivery across SQLite and a remote service. Deployment uncertainty follows the same rule.

Stage 1 now has a real Switch/Discord adapter. From the repository root, run `scripts/up.sh`, then `scripts/status.sh`; see `docs/LIVE-SETUP.md` for account linking and the two-account test. `scripts/simulate.sh` requests a clearly labeled studio-only drill using exactly the three initial sample files. Simulation drafts cannot be released to the client and never record human approvals.

`switch-transport.ts` sends the gate's exact verified snapshot without retries. `main.ts` keeps one all-message WebSocket per room with pongs, saved cursors and reconnects. `visible-loop.ts` wraps the unchanged gate/state machine: intake, one numbered fixed receipt, source files and text room documents, lead drafts, frozen owner releases, and client acceptance. Text extraction currently supports UTF-8 `.md`, `.txt`, and `.csv` up to 100,000 characters; other files are forwarded but lead requests a plain-text export. First publication is version 2, as defined by the existing state machine. Ticket/version numbers include labeled drills.

Switch 0.31.0 emits a null raw sender_kind for ordinary humans and agents. `switch-identities.ts` resolves exact transport IDs against only identity/claim columns in this deployment's own PostgreSQL via Docker; it never guesses names or Discord localparts. This adapter therefore requires the local pinned self-host deployment and Docker access. Varun's release identity is his Switch user ID backed by his explicit Discord account claim. An unlinked human admitted to the private client channel receives the client role; the owner cannot use that role to approve his own brief.

Lead has a separate non-admin Switch owner and studio-only membership. Its addressing policy accepts participants in that private room so desk and the linked Varun can reach it. Source documents are untrusted data read through Switch, with native file/shell tools disabled for lead. This is not OS isolation: both services still run under the same local user. No Stage 2 orchestrator or deployment is started here. The core still does not enforce Switch memberships itself, and there is no automatic uncertain-send retry or replay worker.
